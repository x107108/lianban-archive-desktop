# 给已安装用户发布站内更新提醒

`VERSION.json` 是安装包自己的版本。`updates/latest.json` 是公开的最新正式发布消息，程序只读取这份公开消息，不需要访问令牌、不上传个人数据库或标签。

每次发布共享版时按以下顺序操作：

1. 增加 `VERSION.json` 的版本号，格式为 `年.月.日` 或 `年.月.日.序号`，如 `2026.10.20.2`；重建 `BUNDLE.json`，完成相关测试和安装验收。
2. 提交并推送共享版，打包该提交对应的完整安装 ZIP，在本仓库创建同名标签 `v版本号` 的 GitHub Release，附安装包及 SHA-256 校验文件。
3. 确认 Release 和下载包已公开可访问后，更新 `updates/latest.json` 的 `version`、`title`、`published_at`（含时区）及 `notes`，提交并推送。用户下次后台检查就能收到提示。

消息只对应已公开、可用的正式版本，不能预告尚未发布的版本。下载地址由程序固定生成到本仓库对应的 Release 页面，消息不能指定外部链接。说明使用纯文字，最多 5,000 字符；当前消息保留最新一版。已读消息仍能在站内信查看，有更新版本时重新显示未读标记。

`latest.json` 是发布通知索引，不参与安装包的运行文件校验，因此发布消息的后续更新不会使同版本的安装包校验失效。该索引不用于自动下载安装或同步测试版、服务器版。

2026.10.29.2 起的客户端启动时忽略检查时间缓存而立即检查，之后正常 5 分钟、失败约 1 分钟重试。请求加时间参数和 no-cache，Raw 域名不可达时尝试 GitHub 官方 Contents API 的 raw 响应；不使用发布者凭据。检查失败在页面上明确显示。

有新版时自动弹窗，必须明确选择“去更新”或“稍后提醒”，不能用 Esc 或关闭图标悄悄跳过。稍后在当前页面约 10 分钟再提醒；打开新页面或刷新后重新提醒，已读状态仅用于站内信红点，不控制自动弹窗。用户打开着其他编辑窗口时暂缓弹出，待其关闭。此规则不锁死离线查询，也不自动安装程序。发布新版后，旧包需先实际升级到此客户端一次才会获得新弹窗逻辑。

2026.10.29.3 的真实发布验收发现 Raw 返回 HTTP 200 的旧消息，而 GitHub Contents API 已有新消息。客户端因此每次核对两个来源，分别校验后采用较新版，不再把 Raw 成功等同于消息最新；一处失败保留另一处有效结果。没有有效结果才报告检查失败。
